# Реализация протокола

## 1. Кадр

Кадр состоит из семи и более байт:

| Смещение | Поле | Размер | Кодирование |
| --- | --- | --- | --- |
| 0 | header1 | 1 | A3 |
| 1 | header2 | 1 | A4 |
| 2 | length | 1 | длина payload, 0..255 |
| 3 | wireRand | 1 | rand + 50 по модулю 256 |
| 4 | key | 1 | sessionKey XOR rand |
| 5 | command | 1 | cmd XOR rand |
| 6..6+len-1 | payload | len | payload XOR rand |
| 6+len | crc8 | 1 | CRC8 от всех предыдущих байт |

Важно: wireRand сдвинут на 50, а XOR выполняется с исходным rand. Поэтому при разборе сначала вычисляется rand = (wireRand - 50) & 0xFF, затем этим значением расшифровываются key, command и payload.

CRC8: табличная реализация с отражённым полиномом 0x8C, init 0x00, эквивалент CRC-8/MAXIM с poly 0x31 и refin/refout true. Контрольное значение для строки 123456789 равно 0xA1.

## 2. Сборка и разбор

FrameCodec.build:

1. Проверить длину payload, максимум 255.
2. Сгенерировать rand в диапазоне 1..254.
3. Записать wireRand = rand + 50.
4. Закодировать key, cmd и payload.
5. Посчитать CRC8 и добавить в конец.

FrameCodec.parse:

1. Проверить минимальную длину 7.
2. Проверить A3 A4.
3. Проверить, что длина массива равна length + 7.
4. Проверить CRC8.
5. Восстановить rand, key, cmd, payload.

FrameCodec.findFrames ищет кадры в потоке, пропускает мусор, сохраняет неполный хвост и восстанавливается после кадра с плохим CRC.

## 3. CRC16

CRC16 используется для образа прошивки, а не для обычного кадра. Параметры: полином 0xA001, init 0xFFFF, контрольное значение для 123456789 равно 0x4B37 (CRC-16/MODBUS).

## 4. Рукопожатие

Команда 0x01:

- key в кадре равен 0;
- payload: ASCII-ключ в UTF-8;
- ответ: payload[0] равен 1, payload[1] содержит sessionKey;
- sessionKey 0 допустим;
- таймаут 3000 мс.

DanyScoot не ограничивает длину ключа восемью байтами. Это совместимо с NineHack, где ключ может быть другой длины, но конкретная прошивка может ожидать ровно 8 байт. Для пресетов используются строки 4BKNwi77 и w4S3Hqn5.

## 5. Команды

| Команда | Код | Payload DanyScoot | Назначение |
| --- | --- | --- | --- |
| KEY | 0x01 | ASCII ключ | рукопожатие |
| UNLOCK | 0x05 | 10 байт 01 | разблокировка в стиле NineHack |
| LOCK | 0x15 | 01 | блокировка |
| ERROR | 0x10 | нет TX | уведомление об отклонённой команде |
| DEVICE_INFO | 0x31 | 01 | запрос IoT и устройства |
| SCOOTER_INFO | 0x60 | 01 | телеметрия самоката |
| SCOOTER_SET | 0x61 | headlight, mode, throttle, 00 | фара, режим, газ |
| REALTIME | 0x63 | 01 | батарея, скорость, ток, флаги |
| EJECT | 0x81 | 05 | изъятие батареи |
| FIND_CAR | 0xA2 | 01 | звуковой сигнал |
| RFID | 0x85 | 01 | чтение карты |
| RFID_DELETE | 0x86 | 8 байт | удаление двух карт |
| BATTERY_COVER | 0xC0 | 01 | крышка батареи |
| IOT_RESTART | 0x92 | 01 | перезапуск IoT |
| CLEAR_BT | 0x54 | 01 | очистка привязанных Bluetooth |

Спам-разблокировка использует отдельный payload:

```
01 31 31 32 39 t4 00
```

где 31 31 32 39 - ASCII 1129, t4 - UNIX-время в секундах, big-endian, последний байт 00.

## 6. Расхождение unlock

Восстановлены две формы команды 0x05:

- NineHack: десять байт 01;
- LostBot: 01 31 31 32 39, время в секундах, 00.

DanyScoot использует форму NineHack для обычной кнопки разблокировки и форму LostBot для спама. Это осознанное решение, потому что обе формы подтверждены разными клиентами. Если конкретная прошивка принимает только одну форму, используется соответствующая кнопка или AI-инструмент send_raw_command. Автоматический выбор по ключу не реализован, потому что нет данных о том, что форма зависит от ключа.

## 7. Ответы

| Ответ | Код | Разбор |
| --- | --- | --- |
| KEY | 0x01 | payload[0] статус, payload[1] sessionKey |
| ERROR | 0x10 | payload[0] отклонённая команда, payload[1] причина |
| UNLOCK | 0x05 | payload[0] 1 или 2 - успех |
| LOCK | 0x15 | payload[0] 1 или 2 - успех |
| SCOOTER_SET | 0x61 | payload[0] 0 - успех |
| EJECT | 0x81 | при длине 2 и более payload[0] тег, payload[1] статус, успех при 0 или 1; более короткий ответ считается ACK |
| DEVICE_INFO | 0x31 | ASCII с двоеточием или 7 байт IoT |
| SCOOTER_INFO | 0x60 | 8 байт телеметрии |
| REALTIME | 0x63 | 6 байт телеметрии |
| RFID | 0x85 | 4 байта идентификатора |
| RFID_DELETE | 0x86 | 8 байт двух идентификаторов |
| FW_INFO | 0xFB | статус передачи |
| FW_PACK | 0xFC | индекс, тип, данные, CRC16 |

Ошибка 0x10 отображается как отклонённая команда с причиной. Раньше первый байт ошибочно считался кодом CRC. В текущей реализации payload[0] трактуется как код команды, payload[1] как причина.

Статусы 0x05 и 0x15 противоречивы. LostBot считает 0 успехом, 1 ошибкой, 2 подтверждением. NineHack связывает 1 с успехом. DanyScoot принимает 1 и 2, поэтому на прошивке, которая отвечает 0, возможен ложный отказ в журнале при успешной команде. Это ограничение требует проверки на hardware.

## 8. Телеметрия

Устройство 0x31:

- если payload содержит двоеточие и печатные символы, это текст, например IMEI;
- иначе 7 байт: value u16, flags u8, байт 3 не используется, версия major.minor.patch;
- locked = (flags & 0x01) == 0.

Самокат 0x60:

- battery u8, mode u8;
- speed u16 / 10;
- mileage u16 * 10;
- range u16 * 10.

Реальное время 0x63:

- battery u8;
- speed u16 / 10;
- current u16 / 100;
- flags u8.

RFID 0x85: 4 байта big-endian. RFID_DELETE 0x86: два идентификатора по 4 байта.

## 9. Сессионный ключ

sessionKey приходит в ответе на 0x01 и используется во всех последующих кадрах. Он не равен введённому ключу. После переподключения sessionKey сбрасывается и запрашивается заново.

Если ответ на рукопожатие не получен, sessionKey=0, authenticated=false. Отправка команд блокируется на уровне requireKey и isReady.

## 10. Ограничения реализации

- Нет автоматического повтора команды при потере ответа.
- Нет очереди команд с подтверждением на уровне протокола.
- Нет разбора всех 54 опкодов, только используемых в UI и телеметрии.
- Нет обновления прошивки через приложение. Команды 0xFA, 0xFB и 0xFC читаются и логируются, но загрузка образа не реализована.
- Нет проверки модели самоката по ответу 0x31.
- Нет шифрования канала: XOR и CRC защищают от случайных ошибок, но не от перехвата.
